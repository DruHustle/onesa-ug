# Cybersecurity engineering review

Review date: 5 November 2026. Reviewer role: Cybersecurity Engineer, working as an automated engineering collaborator. Scope: repository source, dependency inventory, authenticated customer/staff/native flows, internal business operations, Company Portal integration, CI and hardware-pilot trust boundaries. This is not independent human approval, a hosted penetration test or a carrier-security certification.

## Decision

The original synthetic preview was appropriately read-only and did not expose real customer data. It was insufficient for physical-pilot operations because staff identity, ownership enforcement, persistent operations and recovery had not been implemented. The current change adds those software controls while retaining explicit prelaunch status and disabled provider effects. A lab pilot can exercise recorded operations with generated credentials. Real subscriber service still requires the externally commissioned integrations and operational acceptance described below.

## Findings and remediation

| --- | --- | --- |
| P0 launch blocker: the preview internal UI was unauthenticated local state | Original web `/internal/` and read-only `src/app.ts` were synthetic; publishing this as a live staff system would provide no access boundary or persistence | Added authenticated platform routes and role/owner checks. Local lab staff require password + TOTP; production requires central identity. Check `src/auth/service.ts`, `src/platform/http.ts`, `src/platform/model.ts`, and platform isolation tests. This was a missing production capability, not confirmed leakage of real records. |
| P0 integration blocker: treating Onesa login as generic JWT bearer validation would be incorrect | Company Portal `src/identity/provider.ts` issues opaque access tokens; current authorization is audience-bound POST `/api/v1/identity/session` | The BFF uses actual Authorization Code, S256 PKCE, state/nonce, Basic client auth and RS256/JWKS validation. Every central session request invokes the live `/session` contract and validates Mobile role, `auth_time` and `amr`; no client-supplied role is trusted. Signed-protocol and revocation tests pass. |
| P1: central Mobile product was absent | Portal product/client schema, SQL role constraints and administration offered only AI/Drone/Robot | Additive Mobile schema, seven roles, default `customer`, opt-in client requirement, staff MFA and migration 015. No account, client secret, access approval or live configuration was created. Generated API contracts were updated. |
| P1: naive Mobile claims could break existing products | AI/Drone/Robot identity consumers accept a fixed three-product vocabulary | Portal `/session` filters Mobile claims for legacy clients while giving the expanded vocabulary to the Mobile client. Regression tests explicitly keep legacy claims unchanged with four clients configured. |
| P1: cross-account reads and role confusion | New persistent applications, support, ledger and export paths require object-level authority | Server predicates use authenticated immutable subject; customer ownership is checked before application/case/receipt access. Staff permission checks run server-side; agent receipt access is limited to its own sales. Separate-customer and least-privilege acceptance tests belong to the platform suite. |
| P1: browser/native credential exposure and replay | Passwords, BFF cookies and custom-scheme callbacks create different trust boundaries | HttpOnly cookies, exact Origin + CSRF for cookie mutations, Secure cookies on HTTPS, random hashed local tokens, encrypted upstream capabilities. Native callback carries only a one-use code bound to a 60-second state/verifier challenge. Replay, wrong state/verifier, expired flow, missing cookie, bad nonce and bad signature tests pass. |
| P1: staff password alone or stale entitlement | Staff can manipulate readiness, customer cases and financial records | All six staff roles require local TOTP or central MFA evidence; original authentication time is retained; sensitive approvals/refunds require recent proof. TOTP replay is rejected atomically. Disable/role changes invalidate local sessions; Portal changes are checked live. |
| P1: issuer outage could prevent logout | An HTTP flow that authenticates against Portal before logout cannot destroy a local token when the provider is unavailable | Added `logoutPresented`: validates local cookie Origin/CSRF, deletes the local capability first and reports central revocation as confirmed/unavailable/not_applicable. It cannot return an authorized business principal. The outage regression passes. |
| P1: accidental commercial activation | Readiness acceptance, test ledger records or hardware observations might be mistaken for real service | Domain state always retains no-network/no-money effects, production registration/charging refusals and uncommissioned provider endpoints. Evidence has scope, expiry and a separate accepting reviewer. A dish/router cannot masquerade as a handset direct-to-cell trial asset. |
| P2: dependency denial-of-service advisories in native build tooling | `glob` GHSA-3g3m-2fjr-6pw4 and `minimatch` GHSA-g3hv-75wg-m249 appeared through Expo CLI/fingerprint; five affected dependency nodes, two root advisories | Scoped overrides pin `glob` 14.0.2 and `minimatch` 11.0.1 under Expo CLI/fingerprint. The locked Expo 58.0.23 / React Native 0.88.1 stack is retained. Production audit reports zero advisories and actual fingerprint generation succeeds; native prebuild/export and compiled-device acceptance remain separately recorded. |
| P2: retry, stale update and audit integrity | Test cash/refund records and commissioning evidence must survive repeat requests without conflicting state | Transactional per-actor idempotency with body/operation conflict detection, revision checks, immutable completed trial observations and an audit hash chain. The chain is locally tamper-evident; a host administrator can rewrite/recompute it, so independent anchoring remains an operational control. |
| P1: a historical lab backup could revive revoked access | Restoring password hashes, roles and disabled flags can undo a password change or access removal made after the snapshot even when old sessions are cleared | Restore disables every lab identity and increments revisions. Operator-only per-user reissue requires an explicit matching expected role, rotates password/TOTP, preserves subject and cannot run in production. Reissue tests prove no bulk enable, no old password/session reuse, role mismatch refusal and rollback when private-file persistence fails. |
| P2: secret/data custody during pilot setup | Default passwords or credentials committed with test data would expose administrative access | CLI generates random secrets into an exclusive 0600 output file, requires staff authenticator setup and refuses existing user/credential overwrite. Production requires an explicit encryption key and refuses lab identities/sessions. SQLite backup, key separation and restore qualification remain operator responsibilities. |

## Verified locally

- Mobile authentication: **24 authentication tests passed**, including RFC TOTP vectors, timing-window replay, scrypt login, role/disabled-session invalidation, CSRF/origin, token hashing and encryption, production/lab separation, restart persistence, credential-file permissions, signed OIDC checks, live permission changes, native handoff and outage logout.
- Mobile backend TypeScript check passed at the authentication integration checkpoint. Root-level platform changes continue to receive their own final check/test run.
- Mobile backend production dependency audit including PDFKit: **zero advisories**. `jpeg-exif` and `crypto-js` deprecation notices in the PDF dependency tree are maintenance concerns, not vulnerability findings in that audit.
- Portal backend: TypeScript check, build, lint, pure Mobile role/MFA policy test, generated OpenAPI validation and contract tests passed. Portal frontend: generated API types, TypeScript check and lint passed.
- Portal migration 001–015 and **7 focused identity cases passed** against a disposable local PGlite engine: three/four-client configuration, existing product assertions, global-administrator MFA, Mobile customer defaults/legacy compatibility, staff MFA/revocation, role constraints and absent-client gates. The PostgreSQL service CI job remains the authority for actual PostgreSQL concurrency and the full existing identity suite. A PGlite run is not evidence for concurrent row-lock behavior, production migration, real mail delivery or hosted OIDC.
- Portal frontend domain/callback suite: **26 tests passed**, including optional fourth exact callback and absent/fifth/foreign callback rejection. Generated contracts match routes and required documentation validation passed.
- Native production dependency audit after scoped overrides: **zero advisories**. The real Expo fingerprint routine completed successfully against the native project.
- Current OpenAPI 3.1 contract: **41 paths / 87 operations**, including public HEAD and explicit preflight. Domain request/record schemas derive from exported Zod models. Five freshness, reference, route-inventory, authorization and mutation-contract tests pass; formal OpenAPI validation passed.
- A separate Principal Engineer reviewed the authentication boundary and found no fail-open path in this scope. Automated role review does not substitute for independent human release approval.

The legacy Portal hygiene script refused to scan because its standalone-repository root guard detects the new ancestor monorepo; that script is not reported as passed. Perform the monorepo publication hygiene gate on the final selected paths. No external system was modified by these checks.

## Required deployment acceptance

These are concrete boundaries that cannot be resolved by inventing endpoints or recording a checkbox:

1. **Central identity:** apply the reviewed Portal migration through an approved, separately qualified Portal release; register one confidential Mobile client with exact HTTPS callback/application origin and secure its client secret. Add the exact Mobile callback to the Portal frontend protocol redirect allowlist. Verify browser and physical native sign-in, all seven role denials, source-session logout, credential change, product revocation and issuer outage against that actual environment. The existing 012-to-014 Portal release helper does not automatically authorize migration 015.
2. **Host and data:** configure the exact trusted proxy addresses, TLS, encrypted volume and protected backups. Restore a backup together with its correct auth key in an isolated environment and prove that production never accepts lab users. Define retention, access, incident contacts and hosting/controller decisions before collecting real subscriber records.
3. **Physical bench:** establish private management access and separate customer/backhaul traffic; replace device defaults; record approved firmware, equipment/approval reference, power/UPS, asset custody and recovery checks. Validate each physical path with actual equipment. A successful Internet test over a Starlink dish cannot qualify handset satellite service.
4. **External providers:** complete the operator, satellite, subscriber-registration and payment contracts; implement their actual commissioned interfaces and reconciliation semantics; verify emergency-service responsibilities and device/network acceptance. No currently implemented route is a substitute for a mobile network, SIM/eSIM provisioning system or payment settlement.
5. **Native delivery:** compile/sign iOS and Android on the appropriate runners, run the physical-device suite and confirm secure storage/callback/sharing behavior. JavaScript export alone does not prove a native build or store readiness.
