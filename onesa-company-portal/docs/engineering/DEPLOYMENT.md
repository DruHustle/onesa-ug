# Deployment and independent releases

An owner-commissioned read-only API observation can recognize an independently
retained Robot staging runtime through its original accepted production API and
exact code equivalence. The external inspector verifies actual immutable images,
configuration and code protection. This preserves that runtime during observation;
it does not qualify or authorize staging, renew a revoked record, or permit any
Robot deployment. Detailed commissioning remains in the protected guide.

An existing API deployment may be observed after a separately released component
changes only through a new operation-scoped external owner commission. The
recovery validates that component’s signed runtime and release chain, preserves
the original plan and all strict unrelated-workload checks, and rechecks the
independent evidence around its read-only observation. No source approval or
deployment request is transferred. See the protected canonical procedure.

Scanner preflight checks the existing disk reserve for both isolated signature
copies before qualification starts. Each copy keeps its own reserve check. Failed
runners retain bounded private diagnostics; those records never authorize retries.

Independent API qualification also requires the existing real conditional-object
ownership and synthetic-cleanup probe. Its transitive module is pinned and mounted
explicitly; missing or failed observations cannot qualify the API.

The external verifier preserves the existing root owner sudo principal when
launching a pinned runner, while excluding ambient credentials. Other principals,
non-root callers and Actions cannot gain that provenance through this handoff.
This correction requires new checked source, installation and qualification;
failed contexts remain consumed.

Frontend staging explicitly selects the provider's preview target before dispatch.
The observed deployment must still match the source, project, region and expected
target before its staging alias is assigned. This source correction requires new
checked source, immutable installation and commissioning; it changes no live runner.

Hosted browser observations check the existing Company and Portal access boundaries
independently. Staging retains its protected preview boundary.

Runtime preservation snapshots wait a bounded time for temporary Docker clients
to finish. Every persistent and unknown workload remains in the snapshot; actual
identity changes, missing services and incomplete observations still block release.

Independent API and worker recipes bind their existing private Compose identity
file by path and digest. Configuration and deployment use that explicit file;
missing, changed or caller-selected identity files fail closed. This correction
requires fresh source qualification and separate commissioning before use.

Static artifact verification accepts generated Next.js catch-all filenames while
retaining canonical path, response-size and byte-digest checks. A verifier fix
requires new source qualification and commissioning; failed contexts stay consumed.

The owner-run backup readback uses a source-pinned transport that drains its output
under pipe backpressure. A truncated read remains a failed check. Installing a fix
requires the normal source qualification and separate commissioning; it does not
replace backup evidence or authorize an application deployment.
Public transport source is copied temporarily for the existing unprivileged
container; installed tools and credentials retain their private custody modes.

Detailed operational instructions are maintained in protected Engineering Docs.
This public source is a reference page, not a deployment or recovery runbook.

The opt-in Docker recovery controller and updated owner verifier share a lifecycle
lock and durable operation holds. Active qualification, deployment, observation
and maintenance suppress recovery; interrupted operations retain their hold for
matching owner reconciliation. A verifier source pin also binds its lifecycle
helper. Existing installations do not acquire this behavior merely from a source
merge. Recovery enrollment binds each accepted full container/image/configuration
identity and must be reviewed again after replacement. It supplies no deployment,
automatic version rollback, migration or physical-actuation authority.

## Oracle owner-run evidence bridge

The new `scripts/release/oracle_owner.py` adapter preserves owner-run receipts
with workflow run ID `0` and genuine CI run references. It requires a separately
commissioned, pinned external verifier and owner-controlled signing custody.
Repository code or an unsigned JSON file supplies no release authority.
The protected guide contains installation, qualification and recovery instructions;
source implementation alone does not establish commissioning or deployment.

The independent shared-scanner adapter is new source. Its installation profile
retains the existing verifier and separate owner commissioning. It requires exact
source, image bytes and current security evidence, isolated streaming/access and
restart checks, recovery evidence and preservation of every independent workload.
One durable request precedes a scanner-only update; inspection cannot repeat it.
A new installation must resolve an earlier uncertain scanner request first.
This implementation statement grants no deployment authority or hosted acceptance.

The Portal-specific frontend extension is new source, not a commissioned service.
It binds public presentation artifacts and existing provider configuration while
retaining the independently deployed API, workers and scanner. Its limited copy scope additionally accepts only the exact default-prefetch
change that prevents speculative page requests. It rejects authentication, hero
or other navigation changes requiring broader qualification. Separate installation, owner commissioning, genuine hosted evidence
and exact-source authorization remain required before release.

The new API runtime adapter is a separate component profile in the existing owner verifier. It binds a reviewed existing-business-code baseline, exact current artifacts and retained configuration, and requires genuine idle-connection recovery in isolated staging. Its single API-only request is durable; production observation is read-only. This implementation statement does not establish installation, commissioning, qualification or deployment.

The extended frontend presentation profile additionally covers the reviewed Drone public routes, images, film, footer, sitemap and enquiry topic. It requires current hosted product/media observations and preserves the existing authentication, Home hero, dependency, privacy and independent-component boundaries. This source change does not extend an older commissioned installation or qualify an existing artifact.


Preview automation uses a no-redirect provider-session request followed by an
exact-host cookie. The complete Robot and Drone browser matrix is validated by
identity as well as count. Failed/skipped/duplicated interactions, foreign origins
or operational mutations cannot qualify. These changes require a new reviewed
source, immutable installation and owner commissioning; the existing failed
reservations and current production operation must never be reset or resubmitted.

The explicit `frontend-nvidia-v1` profile adds current hosted observations for
the reviewed public NVIDIA reference renderer. It retains component `frontend`,
the original presentation gate, existing context/provider budgets and independent
data services. Its policy and target configuration must select the same profile;
the source must equal the newly installed reviewed main and its comparison source
must match the actually retained frontend. All three pinned browser engines must
observe the exact assets, rendering, controls, accessibility and adverse graphics
previews. Local synthetic tests and source implementation do not establish hosted
acceptance, installation or commissioning. Authenticated business workflows,
database restore, simulation and hardware acceptance remain outside this scope.

The API and worker adapters explicitly select each retained service's existing
Compose profile for rendering and deployment. Identity-file pins and independent
service targeting remain mandatory. New source still requires its own checks,
commissioned installation and hosted qualification.

## Private Kubernetes first-install source

`infra/oracle/kubernetes_preflight.py` and `portainer_private.py` preserve the
read-only host assessment and manifest observer. The separate
`infra/oracle/k3s_first_install.py` implements an owner-run first installation;
its `check` action remains read-only. Source tests and a merged change do not
establish installation, owner commissioning or acceptance on a real host. The
existing protected release and maintenance procedures still govern execution.

The installer requires an explicit private plan and verifies selected OCI
IMDSv2 instance identity, the approved destination name and the host fingerprint.
It requires an already enrolled shared-host lifecycle interlock before mutation,
retains its durable maintenance hold after interruption, and does not enable or
replace the existing recovery controller. An existing cluster, partial installation,
unrelated hold, systemd override, missing capacity or overlapping network blocks
the first-install path. Repeating a completed install performs verification only.

`k3s_release_lock.json` binds the stable K3s release binary and packaged images
for the observed architecture, and the compatible Portainer CE image by digest.
The exact copied artifact bytes are checked through one protected file descriptor.
K3s uses its own containerd, an explicit private node/API address, single-node
host-gw networking and private kubeconfig. Traefik, ServiceLB and the default local
storage provisioner are disabled before startup. Its own narrow firewall chains
retain the existing overlay and Docker user policy; no Docker-generated chain is
flushed, no application container is restarted, and no public control-plane or
management UI endpoint is provisioned.

Portainer has HTTPS-only ClusterIP access, denied pod ingress, one observed node,
and an explicit local PV/PVC and storage class with `Retain`. Its data directory
is separate from the K3s datastore. The declared PV size is not a filesystem quota
or a backup. Portainer initially manages Kubernetes only: existing Docker Compose
applications need a separately registered, authenticated private Docker environment
and actual readback before their visualization can be claimed. This installer
does not mount the Docker socket or expose an agent port.

Failure handling stops only the installer-owned service when its file and effective
systemd identity still match. A receipt-write failure does not suppress that stop
attempt. Data, private firewall rules and recovery evidence are retained; remaining
containerd workloads or uncertain ownership require the protected recovery review.
It never invokes the upstream broad uninstall or kill-all scripts. An interrupted
receipt cannot silently restart or authorize reinstallation.

Real host acceptance still requires measured capacity and tenancy-wide cost/quota
headroom, the existing applications' health and preservation checks, actual
CNI/Docker traffic and firewall-order observations, private owner sign-in, external
negative reachability checks, an independently verified datastore/token and
Portainer-data restore, and a controlled reboot/recovery exercise. The existing
2 GiB K3s, 512 MiB UI, 1 GiB host-headroom and 10 GiB disk preparation reserves
exclude additional application workloads. The installer does not resize OCI,
reduce the existing host memory/storage, migrate databases or qualify hardware.
